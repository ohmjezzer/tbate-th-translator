## คำตอบสั้น: ตัวการคือ "โค้ดสเตจ Translation จัดการคำตอบที่ไม่ครบของ LLM ผิด"

LLM แทบไม่เคยตอบครบ 100% ทุกครั้ง แต่เดิมโค้ด **ไม่มีกลไกตรวจ-ซ่อม** เมื่อคำตอบไม่ครบ
มันจึงทำผิด 2 อย่างซ้อนกัน:

1. **ตั้งคำแปล = ข้อความอังกฤษเดิม** (`th = bub.source_text`) → บอลลูนนั้นกลายเป็นอังกฤษ
2. **ยังเอา `glossary.enforce()` ไปรันกับข้อความอังกฤษนั้น** → แทนคำอังกฤษด้วยคำไทย
   กลายเป็น **"ไทยปนอังกฤษ"** ตรง ๆ เช่นเดิมได้ `The มานา Core is unstable, Arthur.`

นี่คือรากของทั้ง "ไม่ถูกแปล" และ "ไทยปนอังกฤษ" ที่เห็น

---

## หลักฐานจาก sandbox (เทียบ "โค้ดเดิม" กับ "โค้ดที่แก้")

เคสจำลอง 5 แบบ + ผลที่ได้:

| เคสจำลอง (พฤติกรรม LLM) | โค้ดเดิม (main) | โค้ดที่แก้ |
|---|---|---|
| ตอบปกติ ทุก id | ไทยครบ | ไทยครบ |
| **ตอบขาด 1 id** (`missing_id`) | `The มานา Core is unstable, Arthur.` ← **ไทยปนอังกฤษ** | `แกนมานาไม่เสถียร อาเธอร์` |
| **ใส่ id ผิดรูปแบบ** (`#bub0`) | ทุกบอลลูนกลายเป็นอังกฤษเต็ม ๆ (3/5 บอลลูน) | ไทยครบ (รอบซ่อมยิงใหม่) |
| **เก็บคำอังกฤษค้าง** (`Mana Core`, `Arthur`) | `แกน มานา Core ไม่เสถียร Arthur` ← ปน | `แกนมานาไม่เสถียร อาเธอร์` |
| **แปลค้างวลีกลางประโยค** | `แต่ the twin horns กลับหายสาบสูญ` ← ปน | `แต่เขาทั้งสองกลับหายสาบสูญไปอย่างไร้ร่องรอย` |
| ตอบว่าง / JSON ขาดกลางคัน | exception → **ทั้งหน้านั้นไม่ถูกแปล** | ข้ามเฉพาะหน้า (หน้าอื่นเดินต่อ) |

ภาพผลลัพธ์จริงของทั้ง 5 เคสหลังแก้: ทุกบอลลูนเป็นไทยล้วน ไม่เหลืออังกฤษ

## ต้นตอ 5 จุด (เรียงตามผลกระทบ)

### 1) Fallback ที่ทำลายคุณภาพ — `translation/llm_translator.py`
```python
th = mapping.get(bub.uid, "").strip()
if not th:
    th = bub.source_text          # ← (ก) บอลลูนเป็นอังกฤษ
th = self.story.glossary.enforce(th)   # ← (ข) แล้วยังเอา glossary มาแทนคำในข้อความอังกฤษ
```
เกิดเมื่อ (ก) LLM ไม่ส่ง id นั้นมา (ข) ส่งมาแต่ `th` เป็นค่าว่าง (ค) LLM เปลี่ยนรูปแบบ id
**ซ่อม:** แยกสองเส้นทางชัดเจน — ได้คำแปลจริง → enforce; ไม่ได้คำแปล → ตาม `on_missing`
(`keep_source` = คง "อังกฤษล้วน" ไม่ผ่าน glossary จึงไม่ปนไทย / `blank` = เว้นว่าง)
พร้อมติด `meta.untranslated=true` + `meta.source_text` ให้หน้า preview เห็นว่าต้องแก้

### 2) ไม่มีการตรวจ/ซ่อมคำตอบ — เพิ่ม `_verify_and_repair()`
เดิมยิง 1 ครั้งแล้วจบ **ซ่อม:** แบ่งเป็นชุดย่อย (`batch_size=12`) แล้วตรวจว่าครบทุก id และ
ไม่มีคำอังกฤษค้าง → ถ้ามี ส่ง "รอบซ่อม" (`repair_passes=1`) เฉพาะรายการที่มีปัญหา
พร้อมกำชับ "ตอบครบทุก id / ไทยล้วน / ห้ามตอบว่าง"

### 3) `glossary.enforce` แทนคำผิดลำดับ — `translation/glossary.py`
ไล่ตามลำดับ dict ทำให้ `Mana` ถูกแทนก่อน `Mana Core` → เหลือ `มานา Core` = ไทยปนอังกฤษ
**ซ่อม:** เรียง "คำยาวก่อน" (longest-first) + เพิ่ม `allowed_latin()` เพื่อรู้ว่าอังกฤษคำไหน "อนุญาต"

### 4) ข้อความขยะจาก OCR ถูกส่งไปแปล
`"... . . . | |"` (อ่านได้แต่เครื่องหมาย) → LLM ตอบว่าง → เดิม fallback เอาขยะมาแสดง
**ซ่อม:** `_is_translatable()` ข้ามบล็อกที่ไม่มีตัวอักษรเลย (ยกเว้น SFX)

### 5) หน้าเดียวพัง = ทั้งเรื่องไม่ถูกแปล — `pipeline.py`
`run()` เดิมเรียก `process_page` โดยไม่มี try/except → พอหน้าที่ N ล้ม (JSON ขาด/เน็ตสะดุด
จน retry ครบ) exception ลอยขึ้นทำให้ **ทุกหน้าหลังจากนั้นไม่ถูกประมวลผลเลย**
ผู้ใช้จึงเห็น "บางหน้าไทย บางหน้าอังกฤษ"
**ซ่อม:** จับ error ระดับหน้า + log + เดินต่อ (ทดสอบ: 3 หน้า, หน้าที่ 2 พัง → ได้ผลลัพธ์ 2 หน้า)

## ค่าตั้งใหม่ที่เพิ่ม (ปรับผ่าน .env ได้)

| env | ค่าเริ่มต้น | หน้าที่ |
|---|---|---|
| `SCANLATION_TRANSLATION_BATCH_SIZE` | 12 | แปลกี่บล็อกต่อ 1 การเรียก (กัน JSON ขาดกลางคัน) |
| `SCANLATION_TRANSLATION_REPAIR_PASSES` | 1 | รอบซ่อมเฉพาะบล็อกที่คำแปลขาด/ปนอังกฤษ (0 = ปิด) |
| `SCANLATION_TRANSLATION_ON_MISSING` | keep_source | เมื่อซ่อมไม่สำเร็จ: คงอังกฤษล้วน หรือเว้นว่าง |

## ข้อจำกัดที่ยังเหลือ (พูดตรง ๆ)
- ถ้า LLM "ดื้อจริง" (ซ่อมแล้วยังเหลืออังกฤษ) โค้ดทำได้แค่ **เตือน + ติดธง** `meta.leftover_english`
  ไม่สามารถบังคับให้ LLM แปลได้ — ต้องแก้ที่ prompt/โมเดล หรือแก้ในหน้า preview
- `glossary.enforce` เป็นการแทนข้อความแบบตรงตัว ถ้าคำแปลไทยมีคำนั้นอยู่แล้วอาจซ้ำคำเล็กน้อย
  (เช่นได้ "แกน แกนมานา") — เป็นเรื่องการตกแต่ง ไม่ใช่ไทยปนอังกฤษ
